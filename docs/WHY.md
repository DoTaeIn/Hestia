# 왜(Why)를 1급 시민으로 — Hestia 차별점 계획

> 상태: 확정 · P0~P2 구현 완료, 로컬 DB 검증 완료 · 최종 수정: 2026-08-16
> `docs/PLANNING.md` 의 비어 있던 Positioning 항목을 채우는 문서다.

## 1. 한 문장

**Hestia의 버전은 텍스트가 아니라 이유를 보존한다.** 본문이 지워져도 왜 지웠는지는 남고, 그 이유는 검색되고 링크된다.

## 2. 왜 베낄 수 없나

Notion·Confluence의 가치 제안은 "마찰 없는 작성"이다. 저장할 때 이유를 묻는 건 그 제안의 반대다.
데이터 모델(`reason text` 한 칸)은 하루면 베낀다. 베낄 수 없는 건 **그 칸을 채우게 만드는 제품 규범**이다.
근거: CompanyOS가 "결정에는 반드시 이유"라는 같은 원리로 실제 작동하는 걸 확인했다.

## 3. 출발점이었던 격차 (해소됨)

`page_revisions` 는 `page_id, version, title, content, created_by, created_at` 뿐이었다.
무엇이 바뀌었는지만 저장하고 왜 바뀌었는지는 안 저장했다 — Notion과 같은 모델이라 차별점이 성립하지 않았다.
`0015` 가 `reason` 칸을 만들면서 이 격차는 닫혔다. 남은 문제는 스키마가 아니라 **그 칸이 실제로 채워지는가**다(§4).

## 4. 마찰 설계 — 이 계획의 핵심 리스크

마찰이 위키를 죽인다. 그러므로 **강제하지 않는다. 비대칭 보상으로 만든다.**

| 원칙 | 구현 |
|---|---|
| 이유 없이도 저장된다 | `reason` 은 nullable. 저장 경로는 지금과 동일하게 동작 |
| 항상 묻지 않는다 | 되돌리기 어려운 변경에서만 묻는다 (§5.2) |
| 나중에 채울 수 있다 | 히스토리에서 지난 판의 이유를 뒤늦게 입력 |
| 채우면 보상이 있다 | 이유 있는 판만 타임라인에 이름표를 갖는다. 이유 없는 판은 접혀서 뭉쳐진다 |

**폐기 기준(kill criteria):** 실사용 2주 뒤 이유 입력률이 저장 건수의 20% 미만이면 마찰 설계가 틀린 것이다. 컬럼을 남기고 프롬프트를 끈다.

## 5. 단계

### P0 — 칸을 만든다 (마이그레이션 1개) · **완료 2026-08-16 · 로컬 검증 완료**

- `supabase/migrations/0015_revision_reason.sql` — `page_revisions.reason text` (nullable)
- `save_page_version(..., change_reason text default null)` / `restore_page_revision(..., change_reason text default null)`
  - 파라미터명이 `reason` 이면 plpgsql INSERT 에서 컬럼명과 모호해진다 → `change_reason`
  - 파라미터를 늘리면 기존 시그니처와 오버로드가 되어 호출이 모호해진다 → 옛 함수를 `drop` 후 재생성
  - 빈 문자열은 `nullif(btrim(...), '')` 로 null 로 눕힌다. `''` 와 `null` 이 섞이면 입력률 집계가 망가진다
- `lib/pages.ts` 의 `PageRevision.reason`, `app/editor/[id]/page.tsx` select
- 이력 목록에 이유 표시 (`.revision-reason`). 이유 없는 판은 지금과 똑같이 보인다
- 복원 모달에 이유 입력 — 명시적 행위이고 "왜 되돌렸나"가 가장 필요한 순간이라 여기부터 물었다. 비워도 복원된다

적용: 로컬 스택에 반영·검증 완료 (2026-08-16). 원격 프로젝트는 아직 link 되어 있지 않다.

여기까지가 되돌릴 수 없는 부분이다. 나머지는 전부 이 위에서 뗐다 붙였다 할 수 있다.

### P1 — 언제 묻는가 · **완료 2026-08-16 · 로컬 검증 완료**

판정은 `lib/pages.ts` 의 `needsReason(before, after)` — 순수 함수라 `lib/pages.test.ts` 로 검증한다 (`npm test`).
저장 시 아래 중 하나면 이유 입력을 띄운다:

- 제목이 바뀜
- 본문 평문이 `REASON_SHRINK_CHARS`(40자) 이상 줄어듦 — 문단 삭제로 간주

건너뛰기("이유 없이 저장") 버튼이 항상 있다. **서버는 검사하지 않는다.**

빈 문서의 표시용 자리표시자 `"(내용 없음)"` 는 길이 계산에서 0으로 눕힌다.
안 그러면 짧은 문서를 통째로 비운 편집이 "8자짜리 내용으로 바뀐 것"이 되어 가장 되돌리기 어려운 변경에서 오히려 안 묻는다.

**나중에 채우기** — 이력 목록에서 이유 없는 판에 "왜 바꿨는지 기록하기", 있는 판에 "고치기".
`0016_backfill_revision_reason.sql` 의 update RLS 정책 + `grant update (reason)` 만으로 열었다. RPC 없음 — 컬럼 grant 가 `reason` 외 수정을 막고, 행 범위는 기존 `can_edit_workspace()` 가 판정한다.

### P2 — 이유가 검색·링크 대상이 된다 · **완료 2026-08-16 · 로컬 검증 완료**

- `search_workspace(term)` RPC 하나가 `pages.search_text` 와 `page_revisions.reason` 을 함께 훑는다. 결과에 "변경 이유 v3" 배지가 붙고, 건수도 따로 센다
- 이력 패널의 "이 문서가 지금 모습이 된 이유들" 토글 — 이유가 적힌 판만 남긴다. 본문에서 지워진 문단의 이유도 여기 남는다. 새 라우트를 만들지 않은 건 같은 데이터를 두 화면에 두면 둘이 갈라지기 때문

여기서 비로소 §1의 문장이 참이 된다. P0·P1만으로는 "커밋 메시지 달린 위키"에 불과하다.

### 검색 이관 (P2와 같이 감) — `0017_search.sql`

옛 검색은 워크스페이스의 모든 페이지를 브라우저로 보내 `includes()` 로 걸렀다.

- `document_plain_text(jsonb)` — ProseMirror JSON 에서 평문만. `pages.search_text` 생성 열의 재료
  - **`jsonb_path_query(doc, '$.**.text')` 를 쓰면 안 된다.** lax 모드에서 `**` 가 배열을 풀어헤치며 같은 노드에 두 경로로 도달해 본문이 두 번 나온다. 실제로 겪었다 — 문서에 한 번 있는 문장이 `search_text` 에 두 번(59자, 고친 뒤 32자). `content` 배열만 따라 내려가는 재귀 CTE 로 바꾸고 `path` 로 정렬해 문서 순서를 지켰다
- `gin (… gin_trgm_ops)` 인덱스 — `pages.search_text`, `page_revisions.reason`
- 본문 전체가 아니라 맞은 자리 앞뒤만 잘라 보낸다 (`lib/search.ts` 의 `snippet`)

**tsvector 가 아니라 pg_trgm 인 이유:** `to_tsvector` 는 낱말 경계로 자르는데 한국어는 조사가 붙어("문서를") 형태소 분석기 없이는 "문서"로 못 찾는다. 형태소 분석기 도입은 아직 사람이 정할 항목이라, 그 결정을 강요하지 않는 쪽을 골랐다. trigram 은 부분 문자열 매칭이라 기존 UX 와 결과가 같다.
대가는 **관련도 순위가 없다는 것**. 순위가 필요해지면 그때 형태소 분석기 + tsvector 를 얹는다.

이 대가를 처음 받아들일 때의 근거는 "사내 위키 규모라 괜찮다"였는데, **2026-08-16 SaaS 로 확정되면서 그 근거가 사라졌다.** 고객사가 늘면 워크스페이스당 문서 수도 예측할 수 없다. 판단 자체를 뒤집을 이유는 아직 없지만(형태소 분석기 결정은 여전히 미정이고 trigram 은 그 결정 없이 돈다), **"규모가 작아서 괜찮다"는 더 이상 쓸 수 있는 논거가 아니다.** 순위 도입 시점은 실제 문서 수를 보고 정한다.

## 6. 하지 않는 것

- 별도 `decisions` 테이블 — 이유는 판에 붙는다. 판에서 떼면 되돌리기와의 연결이 끊긴다
- 이유 필수화 / 승인 워크플로 — 마찰 설계와 정면 충돌
- AI 이유 자동 생성 — 자동 생성된 이유는 이유가 아니다. 그 순간 이 제품의 주장이 거짓말이 된다
- 이유 수정 이력 — 이유는 그냥 `update` 한다. 필요해지면 그때 판다

## 7. 남은 것

- 앱을 띄워 이유 흐름을 손으로 한 번 통과할 것 — 지금까지 검증된 건 SQL 과 순수 함수뿐이다
- 원격 Supabase 프로젝트에 link 되어 있지 않다. `db push` 는 아직 대상이 없다 (사람이 승인할 일)
- **§4의 폐기 기준을 실제로 재는 것.** 이 문서에서 가장 지키기 어려운 약속이다
