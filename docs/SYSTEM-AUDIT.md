# 시스템 정비 기록 — 2026-10-22

Opus가 DB 권한과 공동 편집 계약을, Sonnet 작업들이 워크스페이스·공동 편집 클라이언트·복구를 나누어 구현했다. 통합 감사에서 실제 PostgreSQL 역할과 두 세션 경쟁, Yjs 상태 병합을 실행하고 발견한 문제를 수정했다. 별도로 진행된 디자인 CSS는 유지했다.

## 반영한 동작

- 워크스페이스 선택은 현재 사용자의 멤버십으로 제한한다. 검색·휴지통·이동 링크에도 선택한 워크스페이스를 전달한다. 페이지 재정렬은 하나의 RPC 트랜잭션으로 처리한다.
- 익명 RPC 실행, 비회원 멤버 관리, 관리자 간 권한 변경, 직접 페이지 본문·소유자 변경을 차단한다. 버전 기록·복원은 편집 권한이 있는 문서 소유자에게 허용한다.
- 공동 편집은 하나의 canonical seed와 추가 전용 Yjs 변경 로그를 사용한다. operation UUID 재시도는 중복 저장하지 않으며, 같은 UUID의 다른 내용은 거부한다. 첫 연결과 재연결 모두 DB 로그를 읽는다.
- 복원은 본문·버전·공동 편집 generation을 원자적으로 바꾼다. 모든 공동 편집 RPC는 페이지 → 공동 편집 행 순서로 잠가 복원과 저장 사이의 교착을 방지한다.
- 이전 generation이나 권한을 잃은 세션은 저장과 실시간 연결을 중단한다. 미전송 본문은 사용자·페이지·generation·탭별 복구 데이터로 보존하고, 텍스트 복사와 원본 JSON 내보내기를 지원한다. 이전 generation의 변경을 새 문서에 자동 적용하지 않는다.
- 제목은 버전 기록 시 서버에 저장한다. 기록 전 제목은 탭별 브라우저 초안으로 보관하며, 사용자가 선택해서 불러온다. 저장소가 막히면 보존을 보장한다는 안내를 하지 않는다.
- 이미지의 임시 서명 URL은 에디터 로컬 상태에서만 사용한다. 인증 복귀 경로는 쿼리를 보존하면서 외부 리다이렉트를 거부한다.

## 적용

`0019_system_integrity.sql`, `0020_workspace_operations.sql`을 기존 마이그레이션 뒤에 순서대로 적용해야 한다. 이 작업에서는 운영 DB에 적용하지 않았다. 앱과 DB를 함께 갱신하고 기존 편집 탭을 새로고침해야 한다. 구형 전체 스냅샷 저장 RPC는 새로고침 오류를 반환한다.

공동 편집 RPC 계약:

| RPC | 목적 |
| --- | --- |
| `load_page_collaboration` | seed·generation·해당 generation의 변경 로그 읽기 |
| `seed_page_collaboration` | 최초 seed 조건부 확정, 승자·패자 모두 확정된 seed 사용 |
| `append_page_collaboration_update` | 변경분 저장 및 UUID 중복 검사 |

변경 로그 압축은 구현하지 않았다. 안전하지 않은 checkpoint API는 제거했으며 로그는 다음 복원까지 증가한다. 운영 규모가 커지면 검증된 압축 프로토콜이 필요하다.

## 검증

- `npm test`: 64개 통과. 워크스페이스 선택, 리다이렉트, seed 경쟁, 재접속, 재시도, 복구, 저장소 실패, 권한 상실, 제목 초안을 포함한다.
- `npx tsc --noEmit`, `npm run build`: 통과.
- `supabase/tests/system_integrity.sql`: 278개 중 273개 통과, 5개 명시적 건너뜀, 실패 0. 이 파일은 트랜잭션을 롤백한다.
- `supabase/tests/workspace_operations.sql`: 23개 통과.
- `supabase/tests/system_integrity_concurrency.sql`: 두 실제 DB 세션 검사 12개 통과, 건너뜀 0. 단일 세션 검사에서 건너뛴 seed·복원·load 경쟁을 별도로 검증한다.
- `python3 scripts/test-db-concurrency.py`: 실제 Yjs seed 경쟁, 동시 변경·중복 재시도 후 내용 보존, 복원·저장 경쟁 통과. 추가 검사에서 발견한 교착을 위 잠금 순서로 수정했다.
- 브라우저에서 새 로그인 디자인과 인증 복귀 쿼리를 확인했다.

SQL 검증은 포트를 공개하지 않은 전용 Supabase PostgreSQL 17 컨테이너에서 수행했다. `fixtures/local-services.sql`은 이 환경에만 필요한 최소 Storage·Realtime SQL 스키마와 Auth UID 함수다. 실제 서비스나 운영 DB에 적용하는 파일이 아니다. 이미지의 초기화가 완전히 끝난 뒤 fixture → 모든 마이그레이션 → 테스트 순서로 실행한다. SQL 권한 테스트는 `supabase_admin`으로 실행하고 내부에서 authenticated·anon 역할로 전환한다. pgTAP 결과는 종료 코드뿐 아니라 `not ok`도 확인한다.

동시성 SQL은 fixture를 커밋하므로 폐기 가능한 DB 전용이다. Python 검사는 이름 `hestia-audit-db`, label `codex.task=hestia-system-audit`인 컨테이너만 허용한다. 임의의 원격 DB URL을 받지 않는다.

## 남은 검증 범위

실제 Auth·Storage·Realtime 서비스 전체와 로그인한 편집기 두 브라우저 사이의 종단 간 검증은 하지 않았다. SQL 정책과 클라이언트 상태 병합 통과가 Realtime 서비스 배포 설정까지 검증하는 것은 아니다. 서명 이미지 URL의 장시간 만료 갱신도 추가 확인 대상이다.

회사 중앙 기록의 Windows 경로를 이 Mac에서 사용할 수 없어 중앙 부서 노트를 갱신하지 못했다. 이 문서에 사실·결정·이유·남은 일을 보존한다.

## 추가 기록: 엔진 분리

같은 날 사용자 요청과 방향 확인에 따라 `engine/`에 도메인 타입·권한 힌트·문서 로직·워크스페이스 선택·Supabase 세션 주입 API·공동 편집/복구 코어를 분리했다. 기존 `app/` 화면의 주요 문서·버전·공유·댓글·검색·알림 작업을 엔진에 연결했다. 이유는 동아리용 화면과 이후 SaaS 화면이 같은 권한·저장 동작을 재사용하도록 하기 위해서다. SQL과 권한 정책은 이번 분리에서 바꾸지 않았다.

기존 `lib/pages.ts`, `lib/workspace-context.ts`, `lib/collaboration-sync.ts`, `lib/collaboration-recovery.ts` 경로는 호환용으로 유지한다. 로그인·Storage 이미지 어댑터·표시용 조회 모델·라우팅·디자인은 셸에 있다. 기본 엔진 진입점은 Yjs를 로드하지 않으며 공동 편집은 별도 진입점이다.

최신 단위/계약 테스트는 110개 통과했다. 추가 검사는 역할 매트릭스, 세션 분리, 쿼리의 워크스페이스 범위, 입력 필드 제한, 네트워크 오류, 갱신 행 없음 처리와 엔진의 UI 의존성 경계를 포함한다. 타입 검사와 프로덕션 빌드도 통과했다. [개발자 문서](developers/index.md), [타입 검사되는 예제](../examples/headless.ts)를 추가했다. 실제 서비스 E2E와 원격 DB 적용은 앞서 기록한 대로 남아 있다.

## 추가 기록: 실제 로컬 서비스 적용과 검증

사용자가 후속으로 DB 적용·서비스 검증을 요청한 뒤 범위를 로컬만으로 한정했다. 0019·0020의 부분 적용 이력을 정리하고, 실제 SQL 검사에서 발견한 작성자 FK와 append-only 트리거의 충돌을 0021·0022로 보정했다. 이유는 사용자 계정을 지워도 남은 구성원의 편집 기록이 보존되어야 하기 때문이다. 실제 API에서 첫 workspace INSERT의 RETURNING/RLS 충돌도 수정했다.

실제 Auth·PostgREST·Storage·Realtime 통합 22개, 두 독립 브라우저의 매직 링크 로그인·공동 편집·이미지·버전 기록·신규 workspace/문서 흐름을 통과했다. SQL 278개 중 실패 0·건너뜀 5, workspace 23개 및 작성자 삭제 실제 행 회귀 검사를 통과했다. 로컬은 0022까지 적용됐고 원격은 변경하지 않았다. [최신 검증 기록](LOCAL-VALIDATION.md)에 구체적 결과와 남은 범위를 기록한다. 앞선 실제 서비스 미검증 메모는 이 추가 기록으로 갱신한다.

## 추가 기록: Preview 0.1

프로필 수정·인증 교체 지점·로그인 방식 설정과 소스 공유본을 추가했다. 이유는 동아리에서 이름을 관리하면서도 호스트 개발자가 인증 정책을 선택하게 하기 위해서다. 자격 증명 변경은 인증 제공자에 남기고, DB의 JWT·RLS 경계는 유지했다. 0023까지 로컬 적용, 단위 132개·실제 서비스 31개·프로필 SQL 121개(4개 명시적 건너뜀)·기존 SQL 회귀·빌드·별도 경로 ZIP 설치를 확인했다. 새 설치 SQL도 격리 DB에서 확인했다. 자세한 근거와 한계는 [최신 로컬 검증 기록](LOCAL-VALIDATION.md), 실행 방법은 [Preview 안내](releases/preview-0.1.md)에 있다. 회사 중앙 기록은 현재 Mac에서 해당 Windows 경로를 사용할 수 없어 이 문서와 PLANNING에 누적했다.

## 추가 기록: 보안과 커스텀 역할

사용자가 보안 보강과 직접 역할·권한 생성까지 요청했다. 0024로 문서 편집과 구성원 관리를 분리하고 역할 정의·관리 권한 부여는 소유자만 허용했다. 이유는 운영 담당자를 편집자로 강제하지 않으면서 관리 권한 재위임·소유자 변경을 막기 위해서다. 관리 RPC의 워크스페이스 잠금 후 권한 재확인과 실제 두 세션 검증을 추가했다. 의존성 보안 경고를 패치하고 공개 대기자 파일 쓰기를 제거했다. PHP 런타임은 사용하지 않는다. 로컬 DB 0024, 136개 단위·41개 실제 서비스·45개 역할 SQL과 기존 회귀·빌드·HTTP 검증을 통과했다. 자세한 내용은 [보안 기록](SECURITY-REVIEW.md)에 누적했고 공유본은 Preview 0.1.0-preview.2로 갱신했다. 중앙 노트는 현재 Mac의 Windows 경로 부재로 직접 갱신하지 못했다.

## 2026-10-22 — GitHub 반영 및 문서 게시 완료

- 사실: 사용자의 명시적 요청으로 전체 변경을 기본 브랜치에 커밋·push했다. Pages를 workflow 방식으로 활성화했고 https://dotaein.github.io/Hestia/ 에서 실제 문서 표시를 확인했다. 보안·빌드 CI도 통과했다.
- 결정: 기존 기본 브랜치와 이력을 유지해 fast-forward push했다. 앱 운영 배포·운영 DB 적용은 문서 게시와 별개이므로 변경하지 않았다.
- 해결: 문서 Pages 최초 활성화와 게시. 처음 배포는 활성화 이전 실행으로 실패했으며 설정 후 재실행으로 해결했다. GitHub 연결 앱의 재실행 권한이 없어 기존 Git 자격 증명의 REST API로 실행했다. 비밀값은 저장·기록하지 않았다.
