# 로컬 서비스 검증 — 2026-10-22

사용자가 범위를 **로컬 테스트만**으로 확인했다. 운영 DB, 외부 호스팅, 도메인, Google OAuth 설정은 변경하지 않았다.

최신 Preview 0.1 검증은 문서 끝의 **Preview 0.1 추가 검증**을 참고한다. 아래 0022 기록은 이전 단계의 이력으로 유지한다.

## 적용 환경과 변경

Supabase API `127.0.0.1:55421`, DB `55422`, 앱 `localhost:3010`에서 실제 Auth·PostgREST·Storage·Realtime·Mailpit 서비스를 사용했다. SQL 대역 fixture만으로 검증한 것이 아니다.

| 마이그레이션 | 적용 내용 |
| --- | --- |
| 0019 | 권한·버전·공동 편집 무결성 |
| 0020 | 워크스페이스 검색과 원자적 정렬 |
| 0021 | 이전 부분 적용 DB에 남은 작성자 FK를 `ON DELETE SET NULL`로 정렬 |
| 0022 | FK가 작성자를 NULL로 바꿀 때만 append-only 트리거의 제한적 예외 허용 |

시작 시 이력은 0018까지였으나 0019·0020 객체 일부가 이미 존재했다. 공개 앱 스키마와 이력을 로컬 파일로 백업한 뒤 실제 정의와 적용 이력을 맞췄다. 최종 CLI 확인에서 미적용 마이그레이션은 없었다. 기존 DB 초기화는 하지 않았다.

실제 API에서 첫 워크스페이스 생성 오류를 재현했다. INSERT 직후 representation을 요청하면 멤버십 AFTER INSERT 트리거보다 SELECT RLS가 먼저 평가돼 생성이 거부됐다. 엔진이 INSERT 성공 후 생성한 ID·이름·owner를 반환하도록 수정했고, 실제 API와 온보딩 화면 모두에서 재검증했다.

계정 삭제의 실제 행 테스트에서도 버그를 찾았다. FK의 SET NULL 자체가 UPDATE여서 기존 append-only 트리거가 거부했다. 0022는 중첩된 FK 동작에서 `created_by`만 NULL이 되는 경우를 허용한다. 직접 작성자 변경과 payload 변경은 계속 거부된다.

서비스 검사는 독립 세션 가입, 워크스페이스 생성·초대, 비회원 격리와 역할별 권한, 검색, 댓글·알림, 비공개 이미지 업로드·서명 다운로드, 익명/외부 workspace 이미지 차단, 실제 private Realtime 채널, viewer 발신 거부, Yjs seed 경쟁과 두 세션 수렴, DB 재로딩, HTTP 중복 재시도, 복원 generation, 멤버 제거 후 DB 차단, 휴지통을 포함한다.

단일 세션 SQL 검사에서 건너뛴 항목을 통과로 계산하지 않았다. Realtime 서비스와 Yjs 동작은 별도 실제 서비스 검사에서 확인했고, 이전 두 DB 세션 경쟁 검사 기록은 [시스템 정비 기록](SYSTEM-AUDIT.md)에 있다.

## 실제 브라우저 검증

독립된 IAB·Chrome에서 owner와 editor가 각자 요청한 실제 매직 링크로 로그인했다. 두 화면의 편집 내용이 상대 화면에 반영되는 것을 확인했다. editor의 버전 기록·복원은 비활성화되고 owner는 새 버전을 저장했다.

화면에서 새 동아리 workspace 생성 → 문서 생성 → 본문 작성 → 첫 버전 기록을 통과했다. 이미지 업로드 후 두 브라우저에서 실제 이미지 크기 `1×1`로 로딩되는 것을 확인했고, 저장된 JSON에 `storagePath`가 남고 임시 서명 URL은 포함되지 않음을 API로 검사했다. 로그아웃, 잘못된 링크 안내, 재요청 성공 안내도 확인했다.

브라우저 검사 중 빈 이미지 src 경고를 수정하고, 1시간 서명 URL을 50분마다 재발급하도록 보완했다. MIME 허용 목록도 비공개 버킷의 JPEG·PNG·GIF·WebP와 맞췄다. 설정되지 않은 Google 로그인은 환경 변수로 기본 숨김 처리했다.

검증 스크린샷과 요약 JSON은 Git에서 제외되는 `test-results/local-collaboration.png`, `test-results/local-services.json`에 있다. 테스트 사용자·workspace·이미지·로그인 메일은 정리했다. 원래 켜져 있던 다른 Supabase 프로젝트는 변경하지 않았다.

## 남은 범위

- 외부 SMTP 전달, Google OAuth, 실제 운영 도메인과 네트워크는 이번 범위가 아니다.
- 장시간·대용량·다인 부하는 별도다. 현재 각 편집 transaction이 DB 로그 행과 전체 복구 snapshot 저장을 만들므로, 사용량이 커지면 미전송 update 병합과 snapshot 빈도 제한을 검증해야 한다. 로그 압축은 아직 없다.
- DB가 거부할 정도로 큰 payload의 복구 UX와 영구 오류 분류는 추가 보강 대상이다. 현재 제한된 자동 재시도 뒤 오류로 남는다.
- viewer 화면은 마지막 기록을 표시한다. editor들의 초안 실시간 공유와 viewer의 실시간 구독을 혼동하지 않는다.
- 멤버 제거 시 DB 읽기·쓰기는 즉시 막히지만, 이미 연결된 Realtime 구독의 권한은 토큰 갱신/재접속까지 캐시될 수 있다. 이번 검사는 새 구독 거부와 DB 차단을 확인했다. 지속 연결 수신의 즉시 철회는 보장하지 않는다. [Supabase Realtime 권한 문서](https://supabase.com/docs/guides/realtime/authorization)
- 이미지 재발급 타이머는 구현했지만 1시간 이상 실제 대기하는 검증은 하지 않았다.

로컬 재실행·테스트·fixture 정리 방법은 [실행 가이드](DEPLOYMENT.md)에 있다.

## Preview 0.1 추가 검증 · 2026-10-22

로컬 DB에 0023을 트랜잭션으로 적용하고 CLI 이력을 기록했다. 본인 프로필의 표시 이름·아바타만 수정하도록 컬럼 권한과 제약을 추가했다. 가입 메타데이터 이름을 정규화하고, 다른 계정·생성일 변조·위험한 URL은 차단한다. 로그인은 호스트의 어댑터와 설정으로 분리했다.

| 검사 | 결과 |
| --- | --- |
| 단위/계약 검사 | 132개 통과, 실패 0 |
| 타입 검사 / 프로덕션 빌드 | 통과 |
| 실제 로컬 서비스 통합 | 31개 통과, 실패 0 |

| ZIP의 별도 경로 설치 | `npm ci`·132개 검사·타입 검사·프로덕션 빌드 통과 |

추가 실제 서비스 검사는 프로필 생성·저장·아바타 삭제, 다른 계정 수정 차단, 생성일 변조 거부, 엔진을 우회한 위험 URL 거부, 잘못 주입한 identity에 대한 실제 JWT 권한 거부, 비밀번호 로그인·로그아웃을 포함한다. 로그아웃은 Supabase의 기본 global scope여서 테스트는 새 세션을 다시 수립한 뒤 이어간다.

실제 브라우저에서 비밀번호 로그인, 기본 매직 링크 발급·동일 브라우저 콜백·워크스페이스 진입, 프로필 이름·아바타 URL 저장, 새로고침 후 유지, 아바타 지우기, 계정 메뉴 이름 반영과 로그아웃을 확인했다. 삭제된 계정의 오래된 쿠키가 로그인 페이지를 깨뜨리는 문제를 재현하고, 알려진 세션 거부 오류만 비로그인으로 처리하도록 수정했다. 네트워크·서버 실패는 그대로 오류로 보존한다.

새 설치 검증은 별도 Supabase PostgreSQL 17 컨테이너에서 Auth 기본 스키마와 SQL용 Storage·Realtime fixture를 사용했다. 실제 서비스 검증은 원래의 로컬 Auth·Storage·Realtime에서 별도로 수행했으며, 두 결과를 같은 검증으로 간주하지 않는다. OAuth는 어댑터 계약 검사만 했고 외부 제공자에 로그인하지 않았다.

공유본은 파일 허용 목록으로 생성하고 비밀 키·JWT 형태를 검사한다. ZIP 구조와 파일별 매니페스트·SHA256을 검증했다. 프로필 스크린샷은 Git/공유본에서 제외되는 `test-results/preview-0.1-profile.png`에 있다. 테스트 계정·워크스페이스·이미지·메일·임시 검증 컨테이너와 개발 서버를 정리했고 최종 로컬 DB는 사용자 0·워크스페이스 0·Storage 객체 0·스키마 0023이었다. 원래 실행 중이던 Supabase 서비스는 유지했다.

공유본 생성에는 macOS/Linux의 `zip`·`unzip`이 필요하다. ZIP 수신자가 앱을 설치·실행하는 데에는 이 명령들이 필요하지 않다. 운영 배포·외부 발행은 수행하지 않았으며 위의 남은 범위는 계속 유효하다.

## 보안·커스텀 역할 추가 검증 · Preview 0.1.0-preview.2

로컬 DB는 0024까지 적용했다. npm 감사 경고 0, 단위 136개·실제 서비스 41개·커스텀 역할 SQL 45개와 기존 SQL 회귀 검사를 통과했다. 두 DB 세션의 강등/관리 요청 경합과 비로그인·위조 미들웨어 HTTP 접근 차단도 확인했다. 새 설치 번들은 격리된 빈 DB에서도 0001–0024 적용 후 SQL 회귀 검사를 통과했다. 역할 생성·배정·수정·일반 구성원 관리 조작 제한·커스텀 본문 편집 저장을 브라우저와 DB에서 확인했다. 구체적인 변경·검증 방법·한계는 [보안 기록](SECURITY-REVIEW.md)을 기준으로 본다. 앞의 0022·0023 검증은 이전 단계의 이력이다.


## 최종 보안 검증 — 2026-10-22 / preview.3

최신 결과는 [보안 검증 보고서](SECURITY-REVIEW.md)에 정리했다. 단위 173건, 실제 Auth·Storage·Realtime 53건, 세션 보안 SQL 44건이 통과했다. production 브라우저에서 비밀번호/OTP 로그인·감사 로그·비공개 이미지를 확인했다. 로컬 볼륨 보존 재시작 후 MFA·문서·Yjs 로그·감사 기록·이미지가 유지됐다. 이는 운영의 재해 복구 검증을 대신하지 않는다.


최종 공유본 확인: 별도 빈 Supabase Postgres에 0026 설치 번들을 적용하고 6종 SQL 회귀와 운영 DB 점검을 통과했다. 기존 DB 재설치는 정상 차단됐다. ZIP을 새 폴더에 풀어 npm ci·173개 단위 테스트·타입 검사·production 빌드를 통과했다. 합성 사용자·워크스페이스·감사 이벤트·Storage 파일·MFA factor를 모두 정리했고 로컬 데이터 각 0건을 확인했다.
